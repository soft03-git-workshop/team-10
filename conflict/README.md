# 発展課題：2つの変更を組み合わせる

2つのIssueから別々に変更を作り、コンフリクトを解消して1つのページにまとめます。

1・2周目が終わり、講師から開始の案内が出たteamで取り組みます。

## 役割を決める

4〜6人のteamで、講座名を入れる人とteam名を入れる人を1人ずつ決めます。それぞれ自分のPCで作業します。残りの人は、Issueの意図の確認、解消時の相談、プレビュー確認、PRのレビューを担当します。

| 役割 | 取り組むIssue |
|---|---|
| 講座名を入れる人 | [何の講座のページか分かるようにする](https://github.com/soft03-git-workshop/team-10/issues/16) |
| team名を入れる人 | [どのteamのページか分かるようにする](https://github.com/soft03-git-workshop/team-10/issues/17) |

この演習中は、この2つ以外のPRのマージを待ちます。レビュー相手は役割に合わせて決め、PR作成者以外の人が承認します。

## 1. 同じmainから始める

実装する2人とも、リポジトリのフォルダーで次を確認します。

```bash
git status
```

前の作業の変更が残っている場合は、先にその作業を完了するか講師・サポートに相談します。変更が残っていないことを確認してから進めます。

```bash
git switch main
git pull --ff-only
git rev-parse HEAD
```

最後に出るcommitのIDが2人で同じことを確認します。`conflict/practice.md`の先頭行が `# 自己紹介` になっていることも確認します。異なる場合は、ブランチを作る前に講師・サポートに相談してください。

## 2. 2つのPRを用意する

それぞれ自分のIssueを読み、`feature/そのIssueの番号` というブランチを作ります。自分の担当の変更をcommit・pushしてPRを作り、Discordの自分のteamのチャンネルでレビューを依頼します。

**両方のPRができるまで、どちらもマージしません。** PRができたことを互いに伝えてから次へ進みます。

## 3. 講座名を入れるPRを先にマージする

講座名を入れるPRをレビューし、必要な修正を終えて承認したら、PR作成者がマージします。

team名を入れるPRでは、mainとのコンフリクトが表示されます。表示が更新されない場合は、少し待ってPRを再読み込みしてください。

2人が同時に編集した瞬間に衝突するわけではありません。同じ箇所を異なる内容に変えた履歴を統合するときに、Gitが自動で決められなくなります。

## 4. team名を入れたブランチにmainを取り込む

ここからの操作は、team名を入れた人のPCで行います。相手と相談しながら進めてください。

```bash
git branch --show-current
git status
```

自分の作業ブランチ `feature/17` にいることと、変更が残っていないことを確認します。mainにいる場合は、自分の作業ブランチに切り替えてから進めます。

```bash
git fetch origin
git merge origin/main
```

`CONFLICT` や `Automatic merge failed` が表示されます。この演習では想定した状態です。続けて、どのファイルで起きているかを確認します。

```bash
git status
```

## 5. 最終的な内容を相談して書く

`conflict/practice.md`をエディターで開きます。`<<<<<<<`、`=======`、`>>>>>>>` で囲まれた部分が、Gitが自動で決められなかった箇所です。

この手順では、`HEAD`側がteam名を入れた自分の変更、`origin/main`側が先にマージされた講座名の変更です。VS Codeで「現在の変更」「入力側の変更」と表示される場合も、実際の内容を読んで確認してください。

考えるヒントは2つです。

- それぞれのIssueは、読む人に何が伝わるようにしたい？
- その両方を満たすには、どんな見出しと本文にすればよい？

冒頭の1つの見出しから講座名とteam名が分かる形に書き直し、区切りの記号を取り除きます。「両方を採用」で2つの見出しが残った場合も、完成条件を満たす形に整えてください。

今回、相談して書き直す箇所は見出しです。ファイル全体も読み、講座の説明とteamの紹介がどちらも残っていることを確認します。

## 6. 確認・commit・pushする

VS CodeなどのMarkdownプレビューで、見出しと本文を確認します。ローカルでプレビューできない場合は、push後にGitHubで自分の作業ブランチのファイルを開き、承認・マージの前に確認してください。

内容を確認してから、次を実行します。

```bash
git add conflict/practice.md
git diff --cached --check
git diff --cached
```

`git diff --cached --check`に何も表示されないことを確認します。競合の記号が残っているなどの指摘が出たら、直してからもう一度 `git add conflict/practice.md` を実行し、確認し直します。

続く差分表示で、取り込む内容を確認します。長い表示を終了するときは `q` を押します。問題がなければcommit・pushします。

```bash
git commit -m "講座とteamの変更を統合"
git push
```

記号が消えていても、Issueの目的を満たしているかは人が確認します。

## 7. 同じPRで再レビューを受ける

PRは作り直さず、説明欄を更新します。

- 「変更内容」：どの内容を組み合わせたか、なぜその形にしたか。
- 「動作確認」：プレビューで何を確認し、どう表示されたか。

Discordの元のレビュー依頼のスレッドで、修正したことを伝えて再確認を依頼します。具体的な指摘や承認はGitHubのPRに残します。

レビューする人は、両方のIssueと解消後の差分・プレビューを確認します。必要な修正と再確認を終えてから承認し、PR作成者がマージします。push前の承認が取り消されている場合も、改めて承認が必要です。

最後に、team全員が手元のmainを更新し、完成したファイルを確認します。

```bash
git switch main
git pull --ff-only
```

## 困ったとき

まず `git status` を確認し、画面を残して講師・サポートに相談してください。

手順4で始めた取り込みを中止して、取り込む前の自分のブランチへ戻したい場合は、mergeの途中で次を使えます。今回の解消のために行った編集も取り消します。

```bash
git merge --abort
```

開始前の変更が残っていなかったことが前提です。commit済みなど状態が分からない場合は、そのまま相談してください。
